# hotel-parser — инструкции для Claude

Pet-проект: парсит отели с Booking/Trip/Ostrovok + собирает интерактивную HTML-карту города (отели по ценам, метро, достопримечательности с фото и приоритетами, современные «интересные места» 2025-2026 с категориями) + Excel-отчёт. Сейчас сконфигурирован на Минск.

**Типичная задача:** «сделай такую же карту для города X на даты Y» — алгоритм ниже.

## Архитектура

- **`hotel-parser.js`** — Playwright-парсер трёх источников (не-headless, нужно решать капчи руками). Пишет append-only JSONL-чекпоинт `output/run_<ts>/hotels.jsonl` после каждого отеля + финальный `output/latest.json`.
- **`build-report.js`** — генератор отчёта. Читает `latest.json` + `hotel-config.json`, выдаёт `output/hotels_<slug>_<date>.xlsx` (5 листов) + `_map.html` (Leaflet).
- **`hotel-config.json`** — единственный source of truth для параметров: город/даты/гости + ручные координаты отелей + метро + достопримечательности + интересные места.

## Алгоритм: карта для нового города

### 1. Заполнить базовые поля `hotel-config.json`

Скопируй структуру Минска. Поменяй только:

- `город`: название, страна, `query_booking`, `query_trip`, `cityid_trip` (если знаешь Trip ID — иначе оставь null), `lat`/`lng` центра, `slug` (lowercase ASCII).
- `даты`: ISO `YYYY-MM-DD` для заезда/выезда. По умолчанию строй на 3 ночи; не ограничивайся жёстко — пользователь может хотеть 2 или 5.
- `гости`: взрослых/номеров.

Координаты центра →
```bash
curl -s 'https://nominatim.openstreetmap.org/search?q=<city>&format=json&limit=1' \
  | jq '.[0] | {lat,lon}'
```

### 2. Собрать контент карты — параллельно через research-агенты

Это самая объёмная часть. Делегируй **одновременно** (один Agent-вызов с `run_in_background: true` для каждой темы):

#### a) Метро (если есть в городе)

Запросить у агента: все станции с координатами, номер линии, флаг `пересадка` для пересадочных. Источник: ru/en Wikipedia «Список станций X метрополитена» + кросс-проверка через OSM Nominatim. Точность ±50 м.

Цвета линий, используемые в `build-report.js`:
- Линия 1 → `#CC0000` (красный)
- Линия 2 → `#0055AA` (синий)
- Линия 3 → `#168E44` (зелёный)
- Линия 4+ → потребуется добавить в объект `colors` внутри `buildHtmlMap()` (там два места: polyline + label).

#### b) Ручные координаты топ-отелей

Для 10-15 хорошо известных сетевых отелей города (Hilton, Marriott, Renaissance, Crowne Plaza, Ibis, Holiday Inn, Hyatt, Radisson, Novotel, локальные знаковые отели). **Зачем это нужно:** Nominatim для адресов с номерами домов часто врёт на 0.5-1.5 км. Manual override через substring-match по имени отеля бьёт это.

Координаты — напрямую из OSM по имени:
```bash
curl -s -A 'hotel-parser/1.0' \
  'https://nominatim.openstreetmap.org/search?q=DoubleTree+by+Hilton+<City>&format=json&limit=1&extratags=1' \
  | jq '.[0] | {lat,lon,display_name}'
```

Формат в config (ключ — substring lowercase):
```json
"ручные_координаты": {
  "doubletree": { "lat": 53.9082, "lng": 27.5483 },
  "ренессанс":  { "lat": 53.8921, "lng": 27.5290 }
}
```

Включай и латиницу, и кириллицу, и переводы (Renaissance/Ренессанс) — парсер отдаёт разные варианты с разных сайтов.

#### c) Достопримечательности (5-10 классических)

Поля: `название`, `описание` (1-2 предложения), `lat`, `lng`, `тип` (одиночный emoji), `приоритет` 1-3 (3=топ, 1=если останется время), `фото` (массив URL).

**Фото берём через Wikipedia REST API**, по 1-3 на точку:
```bash
# 1. Получить главное фото статьи:
curl -s 'https://ru.wikipedia.org/api/rest_v1/page/summary/<URL-encoded-title>' \
  | jq '.originalimage.source // .thumbnail.source'

# 2. Если вернулась SVG-схема (бывает для площадей/карт), взять JPG из списка images:
curl -s 'https://ru.wikipedia.org/w/api.php?action=query&titles=<title>&prop=images&imlimit=20&format=json' \
  | jq '.query.pages[].images[].title' | grep -iE '\.(jpg|jpeg|png)$' | head -3

# 3. Конвертить File:Title в актуальный thumb URL:
curl -s 'https://commons.wikimedia.org/w/api.php?action=query&titles=<File:Title>&prop=imageinfo&iiprop=url&iiurlwidth=960&format=json' \
  | jq '.query.pages[].imageinfo[].thumburl'
```

**Не валидируй URL программно** через bulk HEAD — Wikimedia рандомно режет 4xx при пачке HEAD-запросов, выкидывая живые URL. На фронте уже стоит `onerror=placeholder` (серый прямоугольник, высота сохраняется), этого достаточно.

#### d) Интересные места (15-25 современных)

Эта часть — главное отличие от Яндекс.Карт. Делегируй research-агенту с конкретными источниками:
- Локальные тревел-блоги города (для Минска: onliner.by, citydog.io; для Тбилиси: bm.ge, agenda.ge; и т.д.)
- WHERETOEAT/Tripadvisor топы 2025-2026
- Reddit r/<city>
- TikTok/Instagram-вирусные точки

**Категории строго эти 5** (ключи и эмодзи зафиксированы в `PLACE_CATEGORIES` build-report.js):
- `еда` — оранжевый `#FB8C00` — рестораны, кафе, фастфуд (включая локальные сети типа Mak.by)
- `тусовка` — фиолетовый `#8E24AA` — бары, караоке, арт-кварталы, концертные площадки
- `шопинг` — синий `#1E88E5` — ТЦ, маркеты, концептуальные магазины
- `природа` — зелёный `#43A047` — парки, набережные, водоёмы внутри города
- `загород` — коричневый `#6D4C41` — точки в радиусе 1-2 часов на машине (замки, этно-музеи, природа)

Поле `тренд: true` для тех точек, что в топах 2025-2026 — на карте они получают бейдж 🔥 в попапе и легенде.

**Загородные точки обязательны.** Минимум 2-3 за пределами города в радиусе 2ч езды (для Минска — Несвижский/Мирский замки, Дудутки; для Тбилиси — Мцхета, Кахетия, Степанцминда). Они отображаются на карте с авто-уменьшением zoom при клике из легенды.

#### e) Фото для интересных мест (опционально)

Wikipedia/Commons — да для парков/замков/инфраструктуры (надёжно). Для современных ресторанов/баров — сложно, hotlinkable публичных URL обычно нет. Если не нашёл — пиши `"фото": []` (либо опускай поле). Не выдумывай URL.

### 3. Запуск

```bash
npm install                      # один раз
npx playwright install chromium  # один раз

# Изменить hotel-config.json под новый город

npm run parse                    # 5-15 минут, не headless — будут капчи
npm run report                   # < 30 сек
open output/hotels_<slug>_*_map.html
```

`npm run parse:booking` / `parse:trip` / `parse:ostrovok` — запустить только один источник.

## Грабли и принципы

### Метод: селекторы снимать со страницы, а не угадывать

Три источника из четырёх ломались именно на выдуманных селекторах. Рабочий приём:
открыть живую выдачу в **том же профиле** (`session/`), найти нужный узел **по
содержимому** (регэксп по валюте) и распечатать его настоящий путь и атрибуты.
Проверять разбор потом можно без браузера: снять реальные строки со страницы в
JSON и прогнать регэкспы по ним — так ловится «взяли не тот узел».

### Agoda

- Карточка — `[data-selenium="hotel-item"]`, id отеля в `data-hotelid`.
- **Цена только из `[data-element-name="display-price"]`** (чистое число) плюс
  `[data-element-name="hotel-currency"]`. Регэксп по тексту карточки брать НЕЛЬЗЯ:
  первым в блоке `property-card-price` идёт бейдж
  `consolidated-applied-discount-badge` вида «С учетом 2 039 ₽» — это **размер
  скидки**. Из-за него в выгрузку попадали 2 039 ₽ за ultra-all-inclusive вместо
  реальных 22 748 ₽. Второй ложный кандидат — `fpc-cor-price`, это зачёркнутая
  цена ДО скидки.
- Период цены не угадывать: `[data-element-name="per-night-begins-with"]` прямо
  пишет «За ночь после налогов и сборов».
- Звёзды — `[data-selenium="ssr-property-card-star-rating"]` («Количество звезд: 5 из 5»),
  рейтинг и отзывы — `[data-selenium="property-card-review"]`, район и расстояние —
  `[data-selenium="area-city"]` («…Нячанг - 20,8 км от центра»).
- **Ленивая отрисовка**: цена появляется, только когда карточка попала в зону
  видимости. Собирать надо ПО ХОДУ скролла, а не один раз в конце.
- Выдача постранична («Стр. 1 из 10»), кнопка `[data-selenium="pagination-next-btn"]`.
  Скроллом другие страницы не добираются. Лимит — флаг `--agoda-pages=N`.

### Trip.com

- Параметр города — `cityId`, а не `city`: со старым `city=<id>` отдаётся пустая выдача.
- Карточка — `div.hotel-card-versionb`, её `id` это id отеля (голое число, не `hotel_<id>`).
  Имя — `a.hotelName`, рейтинг — `span.score`, отзывы — `span.comment-num`.
- **Цена печатается кодом валюты ПЕРЕД числом и с запятой в разрядах: «RUB 4,717»**.
  Шаблоны вида `N ₽` / `N USD` такого не ловят — из-за этого цены не снимались вообще.
- Брать `span.price-highlight` («Total price: RUB 16 048») — это за ВЕСЬ период с
  налогами. Ставка×ночи даёт другое число (4 717×3 = 14 151 ≠ 16 048).
- Отдаёт английскую вёрстку даже при `locale=ru-RU`.
- Список рисуется на сервере, XHR с отелями нет — сетевой перехват бесполезен.

### Booking и Островок: выдача не влезает в одну страницу

- Booking прячет остальное за кнопкой «**Загрузить больше результатов**» —
  именно так, не «Показать ещё». В левых фильтрах он сам пишет, сколько всего
  («Отели 258»): если в выгрузке меньше, значит до кнопки не дожали.
- Островок листается кнопкой «Вперед»
  (`button[data-testid="next-pagination-button"]`), по 20 карточек на страницу.
  Скроллом следующие страницы не приходят.
- **Смену страницы у Островка ловить по `page=` в URL**, а не по заголовку первой
  карточки: заголовок лежит не всегда в `h2`/`h3`, из-за чего проверка молча не
  срабатывала и парсер печатал «страницы кончились», уже стоя на `page=2`.
- Число страниц нигде не зашивать. Agoda сама пишет «Стр. 1 из N» — читаем оттуда;
  Островок листаем, пока есть кнопка «Вперед». Флаги `--agoda-pages=N` и
  `--ostrovok-pages=N` — ручное ограничение для отладки, значения по умолчанию
  работают как предохранитель от бесконечного цикла, а не как потолок выгрузки.

**Цена в выгрузке — это «от»:** самый дешёвый доступный номер на даты. Завтрак,
тип кровати и условия отмены у этой ставки не проверяются.

### Google: список постранично, цены — из исходника страницы отеля

Google — метапоиск: он не продаёт, а показывает цены партнёров, и среди них
есть те, кого не парсит никто из остальных четырёх (Traveloka, klook,
Prestigia, Bluepillow, HomeToGo). По Potique на 18-21.08 разница между лучшим
и вторым партнёром — 19%: Traveloka 23 500 ₽ против 29 110 ₽ у Trip.com.

**Даты живут в параметре `ts`,** protobuf в base64url. Собрать его с нуля
нельзя — сервер отвечает 500. Рабочий приём (`googleTs()`): взять живой шаблон
и подменить в нём байты дней и число ночей, длины при этом не меняются, поэтому
внутренние префиксы длин остаются валидными. Дубль на питоне —
`vacation/scripts/google_ts.py`.

**Постраничность есть, но её легко не заметить.** Внизу списка написано
«Результаты 1-18 из 1091», и рядом стоит кнопка «Далее» без подписи: текст
лежит внутри `span`, а сама кнопка неотличима от стрелок каруселей внутри
карточек — у тех такой же класс и такой же `aria-label="Далее"`. Отличается она
единственным: непустым `innerText`. Прокрутка колесом список не растит,
поэтому источник и упирался в 17 карточек, пока пагинация считалась
несуществующей.

**Одного прохода мало: Google обрывает выдачу примерно на 690 карточках,**
хотя счётчик обещает 2750. Обходится сортировками: каждая показывает свои 690
из той же тысячи. Нячанг, 18-21.08 — по релевантности 741, по цене +126,
по оценке +63, по отзывам +11, итого 941 отель за 5 минут.

**«Все варианты» кликом не раскрываются, и не надо.** Кнопка «Показать больше
вариантов» лежит в контейнере нулевой высоты: Playwright до неё не доскроллит
(`scrollIntoViewIfNeeded` виснет на таймаут), а `el.click()` из `evaluate` не
порождает ни одного запроса. Весь список партнёров приезжает с первым же GET
внутри `AF_initDataCallback({key: 'ds:1', …})` — это состояние страницы,
отданное сервером. Поэтому карточка отеля берётся обычным `ctx.request.get`
за полторы секунды вместо пяти на рендер, и её можно тянуть в пять потоков:
941 отель — 3,5 минуты, ноль ошибок.

Узлы в `ds:1` ищем **по форме, а не по пути**: индексы вроде `[0,6,2,21]`
меняются от сборки к сборке. Предложение партнёра узнаётся по тройке
`[название, id, "/travel/lodging/clk?…"]`, цена — по пятёрке
`["7 833 ₽", null, 7833.25, null, 7833]`. Настоящий адрес партнёра лежит
в параметре `pcurl=` ссылки-редиректа.

Оттуда же берутся координаты (`[0,2,0]`), адрес, рейтинг и число отзывов —
у карточек списка их нет. Координаты нужны не для карты, а для планки
«не дальше 8 км»: половина «нячангских» отелей стоит в Камрани за 20-35 км.

Отель без цены — нормальный ответ, а не сбой разбора: на эти даты его никто
не продаёт. По Нячангу таких треть, 300 из 941.

Флаги: `--google-pages=N` (предохранитель постраничности),
`--google-sorts=N` (сколько сортировок пройти, 1 — быстрая проверка),
`--google-no-offers` (только список, без страниц отелей),
`--google-offers-limit=N` и `--google-concurrency=N` — для отладки.

### Открытое: цены Booking завышены, причина не найдена

Google показывает цену Booking по тому же отелю и тем же датам — это
бесплатная сверка, и она у Booking не сходится. На Нячанге 18-21.08, 62
совпадения: медиана отношения «наша цена / цена Booking у Google» — **1.67**,
верхний квартиль 2.33, в пределах ±10% всего четверть отелей. Larosa Hotel:
16 431 ₽ у нас против 7 389 ₽ у Google. Potique: 41 581 ₽ против 29 920 ₽.
У Agoda та же сверка даёт 1.07, у Trip.com 0.99 — там всё в порядке.

**Проверенная и не подтвердившаяся гипотеза:** «в карточке два итога,
перечёркнутый без скидки и настоящий, а `String.match` берёт первый». Итог
в карточке один: выбор минимального из всех совпадений `/N руб за 3 ноч/`
цену не поменял вообще — Larosa как была 16 431 ₽, так и осталась.

Копать дальше стоит в тарифах: похоже, поиск Booking и фид Booking для Google
отдают разные ставки (разный тип номера или разные условия отмены). Пока не
разобрано — **столбец Booking в отчёте считать завышенным**, а решение
принимать по Google, Agoda и Trip.com.

### Логин: проверять, а не верить

Цены зависят от уровня лояльности (Genius, GURU, Trip Rewards, Agoda VIP),
поэтому парсер печатает `🔑 <источник>: вошёл / НЕ вошёл` (`logLoginState()`).

Главное правило детектора: **вход засчитывать только по положительному
признаку**. Проверка «нет слова „Войти“ → значит вошёл» дала ложное
срабатывание на Agoda: она этой кнопки на главной просто не показывает.
Обратное направление надёжно: если кнопка «Войти» на странице ЕСТЬ — точно не
вошёл. У Booking и Островка узел аватара называется не так, как у Agoda, и
`acc` там 0 даже у залогиненного — поэтому вердикт трёхзначный, а не булев.

### Сколько отелей ждать

Нячанг, 16-19.08.2026 (всё под логином): Agoda ~600 (10 страниц), Booking ~250
(сам показывает 258 в фильтре «Отели»; `nflt=ht_id%3D204` оставляет только тип
«Отели», без апартаментов и хостелов), Trip.com ~134, Островок — сколько
наберётся по страницам.

**Логин влияет не только на цену, но и на размер выдачи.** Анонимная сессия
Trip.com отдавала 12 отелей и писала «No additional properties available» —
выглядело как настоящий конец списка. Под логином тот же запрос дал 134.
Так что маленькая выдача — повод сначала проверить `🔑` в логе, а не считать,
что у направления мало отелей.

### Отчёт в проекте vacation

`vacation/scripts/hotels_nhatrang_report.py` раньше жёстко знал только Туту,
Booking и Островок — новые источники молча выпадали. Теперь колонки строятся по
факту наличия (`SOURCE_LABELS` / `SOURCE_ORDER`); при добавлении источника в
парсер дописывать там ничего не надо.

- **Nominatim адреса часто промахиваются** на 500-1500 м даже в больших городах. Поэтому: ручные координаты для known hotels + валидация по метро (см. `geocodeHotels()` в build-report.js: если адрес говорит «X м от метро Y», а Nominatim вернул точку дальше `max(X*2.5, X+400)` от Y — фолбэк на станцию метро).
- **Wikipedia thumbnail URL формат:** только через REST API или MediaWiki API. Выдуманные URL вида `Minsk_Independence_Square.jpg/640px-...` не работают (404). Текущий список фото в config был получен через API — не подменяй на «угаданные».
- **Категории интересных мест** — не вводи новые без обновления `PLACE_CATEGORIES` в build-report.js (цвет, фон, label) И легенды.
- **Загородные точки** — координаты в config используются как есть; в `inCityBounds()` (для отелей) они не проходят, но это проверка только для отелей. Для интересных мест нет проверки bounds.
- **Кликабельная легенда** работает через `markerByName[name] = L.marker(...)`. Имена должны быть уникальны в рамках всех типов маркеров (отели/достопримечательности/места).

## Команды

| Команда | Что делает |
|---|---|
| `npm run parse` | парсер всех трёх источников |
| `npm run parse:booking` | только Booking |
| `npm run parse:trip` | только Trip.com |
| `npm run parse:ostrovok` | только Ostrovok.ru |
| `npm run parse:agoda` | только Agoda.com |
| `node hotel-parser.js --google` | Google: список по четырём сортировкам плюс варианты партнёров по каждому отелю (~9 минут) |
| `node hotel-parser.js --google --google-sorts=1 --google-no-offers` | быстрая проверка, что список вообще собирается |
| `node hotel-parser.js --agoda --agoda-pages=2` | Agoda, но не все 10 страниц |
| `npm run report` | сгенерировать отчёт (xlsx + html) из последнего `latest.json` |
